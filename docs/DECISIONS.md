# Decisions

Format: date, decision, reason. Newest at the bottom.

## 2026-10-24: Toolchain from GitHub release assets
Foundry 1.5.1 and solc 0.8.37 are installed from GitHub release downloads by `scripts/setup.sh`. Reason: foundry.paradigm.xyz and binaries.soliditylang.org are blocked in the build workspace; GitHub releases are reachable. solc 0.8.37 with via-IR and 200 optimizer runs matches the settings under which Skale's XMSS proof was made.

## 2026-10-24: Hash binding uses a public seed, not the account address
Every hash binds a domain type, a random 32-byte public seed, the chain id, the leaf index, the chain index and the step (tree hashes bind level and node index). It does not bind the account address.
Reason: the account address commits (through CREATE2) to code that contains the key-tree root, and the root is built from these hashes. Binding the address inside the hashes is therefore circular. A two-step deploy (address first, root later) breaks the cycle but opens a front-running attack on the deploy frame, which EIP-8141 "Deploy Frame Front-Running" warns about. The public seed is the method of XMSS (RFC 8391) and SPHINCS+: it is unique per account, so it prevents multi-target attacks across accounts in the same way. The address is still bound at the message level, because Profile A signs the canonical signature hash, which covers `sender` and `chain_id`.

## 2026-10-24: D5 revised: sign the canonical signature hash; no fee-bump replacement
Profile A signs `TXPARAM(0x08)` = `compute_sig_hash(tx)`, with the Winternitz bytes in an ARBITRARY signature entry with empty `msg`.
Reason: EIP-8141 states that `compute_sig_hash` covers the whole transaction, fees included, and its Security Considerations ("Execution Approval Authorizes All Subsequent Sender Frames") warn that approving on an explicit 32-byte `msg` authorises an open-ended list of frames. A fee bump would change the hash and so need a second signature on the same leaf (the nonce key is fixed), which breaks one-time security. So the signer sets a generous `max_fee` (only the actual cost is collected) and never replaces a transaction. A custom digest with a signed fee ceiling, which would allow bumps without re-signing, is a stretch goal.

## 2026-10-24: Nonce key = encoded leaf index, single-use
`nonce_keys = [LEAF_KEY_BASE + leafIndex]`, `nonce_seq = MAX_NONCE_SEQ` (EIP-8250 single-use). VERIFY checks key count is 1, the key matches the leaf in the signature, and `nonce_seq == MAX_NONCE_SEQ`. Reason: EIP-8250 now uses a key list and a single-use marker; its Security Considerations say single-use applications must authenticate the key set and sequence and should bind the signature hash. Key 0 is reserved for the legacy nonce, so the base is non-zero.

## 2026-10-24: Winternitz parameter w is a runtime argument of the verifier
The Solidity verifier takes log2(w) in {1, 2, 4, 8} at run time. Profile A uses w = 16. Reason: this lets one tested code path produce measured gas for every row of the frontier table instead of estimates. The overhead is a few shifts per digit.

## 2026-10-24: Nonce sequence 0 instead of MAX_NONCE_SEQ (supersedes part of "Nonce key = encoded leaf index")
The account requires `nonce_keys = [LEAF_KEY_BASE + leaf]` and `nonce_seq == 0`.
Reason: the devnet's ethrex rejects `nonce_seq == 2^64 - 1`, so the EIP-8250 single-use marker cannot be used there. A keyed transaction is valid only if `nonce_seq` equals the key's current sequence, and the first use moves the sequence from 0 to 1. An account that accepts only sequence 0 therefore accepts each leaf once, under both the EIP text and the devnet build. The signer treats a leaf as spent when its NONCE_MANAGER slot is non-zero.

## 2026-10-24: Signer follows the devnet encoding of the signature hash
The TypeScript signer computes the canonical signature hash the way the devnet's ethrex does (elided bytes as empty bytes, three fee fields, recent-root list), with the EIP-text encoding kept as an option. Reason: the account verifies `TXPARAM(0x08)` as returned by the node, so the signer must match the node. A public-devnet admission is only claimed from a saved raw response.

## 2026-10-24: VERIFY limit from exact hash steps
The signer sets the VERIFY frame's execution limit as `26,225 + 81.4 x steps + max residual + 2,000` (fit in results/verify_gas_model.json, regenerated by scripts). Reason: a fixed 90,000 wastes the payer's reserved fee and hides the rare costly message; the exact step count is known before signing. Because the signature hash covers the limit, the limit is settled in a short loop. The worst possible message (990 steps) would not fit the public cap; at the measured spread (420 to 630 steps in 128 samples) this is not expected to occur, and the signer refuses to send one unless told to use the alt mempool.

## 2026-10-24: Profile B = Yul account + Solidity wrapper around Skale XMSS, separate nonce-key tag
Profile B's account STATICCALLs `LamportXmssVerifier`, which decodes the packed signature and calls Skale's `XMSS.verify` unchanged. Its nonce keys use the tag "LMPB", distinct from Profile A's "LAMP". Reason: reuse the Skale verifier rather than rewrite it. A separate contract keeps XMSS.sol byte-identical to the vendored code, and distinct tags keep the two leaf spaces apart even if one key file were used for both profiles.

## 2026-10-24: Local ethrex + sidecar instead of the public devnet
The public devnet hosts and the ghcr.io image layers are blocked here, so ethrex `eip8141-tracer` (9aa3645) is built from source and run locally with the sidecar (fcb4885). The local node does not produce blocks (its dev block producer cannot drive Hegota at this commit), so accounts are placed in genesis and results are simulation and admission verdicts, not inclusions. Every such result file says "LOCAL" and is never presented as a public-devnet admission.

## 2026-10-24: Legacy-nonce mode as an option for Profile A (keyed stays the default)
The account takes a constructor flag: 0 = keyed nonce (leaf i at key LAMP+i, sequence 0), 1 = legacy nonce (leaf = account nonce). Reason: measured on ethrex, the keyed nonce costs 20,000 gas inside the VERIFY frame, which puts the largest observed keyed frame at 92,936 of 100,000; legacy mode measures 58,014 to 72,672. Legacy mode is strictly sequential and, if a signed transaction is dropped, can only continue by rebroadcasting that same signed transaction (the signer does this; it never signs the leaf again). Keyed mode keeps D4 and allows leaves to be skipped. Recommendation for the public mempool demo: legacy mode; for the alt-mempool story: keyed mode.

## 2026-10-24: Deploy the account in a separate transaction
Measured: deploying the account inside the frame transaction needs about 2.49M state gas, over the 500,000 public cap. The account is deployed first through the deterministic deployment proxy (any funded test key may send it; it has no authority over the account), then used with `self_verify`.

## 2026-10-24: Local block production through the Engine API
scripts/local_blocks.py drives ethrex as a minimal consensus client so inclusion can be tested locally. Reason: ethrex's dev block producer cannot build Hegota blocks at 9aa3645. Local results are labelled LOCAL and never presented as public-devnet admissions.

## 2026-10-25: Show the alt-mempool rule fix with a patched sidecar, kept as a patch
The sidecar refuses Profile B for two reasons: a fixed 100,000 budget and an empty precompile allow-list. We keep the upstream sidecar unmodified in the repository and ship a 26-line patch (`patches/sidecar-configurable-verify-budget.patch`, default behaviour unchanged) plus a script that runs it with the precompile list set. Reason: a patch is easy for the sidecar authors to review, and results from it are labelled LOCAL + PATCHED.

## 2026-10-25: Key rotation through stored tree commitments
The account stores `keccak256(seed || root)` per tree at slot `epoch` and the signature carries seed and root; rotation registers epoch + 1 from a SENDER frame of the account calling itself. Keyed mode puts the epoch in the nonce key (`LAMP + (epoch << 16) + leaf`), legacy mode in the nonce (`epoch * 1024 + leaf`). Reason: without rotation an account dies after 1,024 transactions (the strict review's main practicality complaint). Cost: one cold SLOAD of the sender's own storage (allowed in validation), about 2,000 gas, and 64 more signature bytes (not counted toward the cap). Alternatives rejected: storing the root in code (cannot change), reading two slots (seed and root, 4,200 gas), revoking old trees (another SLOAD in every VERIFY). Rotation does not revoke; documented in SECURITY.md. The bench regression bound rises from 72,000 to 74,000 for this reason.

## 2026-11-12: EIP-8141 is not live, so the frame account waits for it
EIP-8141 is a draft. The FAQ at eip8141.io (read 2026-11-12) says it is Scheduled for Inclusion in Hegotá, not on mainnet, and that the implementation and the EIP number may still change. ethereum.org/roadmap/hegota, updated 2026-10-16, expects mainnet in Q2 2027 with no confirmed date. The signer follows ethrex `eip8141-tracer` at 9aa3645, which disagrees with the current EIP text, so a newer frames devnet would reject these transactions until the encoding is updated. ethPandaOps lists bogota-devnet-1 with launch date TBD. Results stay labelled LOCAL until a public frames network accepts them. The public name is HashAccount; contract identifiers stay Lamport so the measured artifacts stay valid. The comparison with other approaches is in `docs/PRIOR_ART.md`.
